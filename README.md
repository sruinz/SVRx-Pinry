<h1 align="center">SVRx Pinry Server</h1>

<p align="center">
  한국어와 대량 이미지 관리에 맞춘 셀프 호스팅 이미지 보드
</p>

SVRx Pinry Server는 개인 서버나 NAS에 설치해 이미지를 보드와 태그로
정리하는 서버입니다. SVRx Pinry 브라우저 확장 프로그램을 사용하면
웹페이지의 여러 이미지를 한 번에 저장할 수 있습니다.

이 프로젝트는 Pinry를 기반으로 만든 비공식 수정 배포판입니다.

## 주요 기능

### 이미지 탐색과 감상

- 반응형 핀 목록과 최신순·오래된순·랜덤 정렬, 작게·보통·크게 카드 크기 및 선택 저장
- 움직이는 GIF·WebP 배지와 이미지 유형·비율·최소 가로/세로·등록일 검색 필터
- 복수 태그 AND 검색, 검색 조건의 URL 반영과 복원, 조건 없는 전체 검색
- 상세보기 이전·다음 이동, 원본 크기·화면 맞춤 전환과 보기 방식 기억
- 전체 화면 및 1·3·5·10초 슬라이드쇼, 다음 원본 미리 로딩으로 전환 대기 완화
- 라이트·다크 테마 전환, 한국어·영어·중국어·프랑스어, 키보드 탐색과 초점 표시

### 보드와 대량 관리

- 보드·태그로 이미지 정리, 선택·범위 선택·전체 선택 및 일괄 수정·이동·삭제
- 보드 추가 시 기존 포함 상태 표시와 중복 추가 방지
- 보드 삭제 시 포함된 Pin 삭제 여부 선택, 관리자 태그 검색·사용량 확인·중복 병합
- 선택 Pin과 소유 보드의 원본·XMP·매니페스트 ZIP 내보내기와 백그라운드 작업 진행 확인
- 원본 파일명 보존·동일 이미지 중복 저장 방지, 원본과 썸네일·파생 이미지 분리
- 브라우저 확장 프로그램의 다중 이미지 수집과 일괄 Pin 생성 API

### 계정과 운영

- Authentik·Synology·Google·Microsoft·GitHub·범용 OIDC 로그인과 제공자별 설정 가이드
- 검증된 이메일의 기존 계정 자동 연결, SSO 신규 가입 시 아이디·로컬 비밀번호 설정
- 비밀번호 로그인·API 토큰 정책 분리와 내부망 직접 접속용 관리자 복구 로그인
- 프로필·토큰·SSO·관리자 카드 통합, 토큰 기본 마스킹과 표시·복사 기능
- 프로필에서 실행 커밋 및 백엔드·프런트엔드 의존성 버전을 버블 UI로 확인
- 기존 Pinry 데이터 자동 백업·마이그레이션, 레거시 설정 호환 보완과 한국어 진행·복구 화면
- Synology NAS용 Docker 빌드 산출물과 데이터 보존형 업그레이드

## 현대화된 실행 환경

기존 Pinry의 보드·태그·이미지 관리 흐름을 유지하면서 실행 환경과 화면을 갱신했습니다.
현재 소스의 주요 의존성은 다음과 같습니다. 실제 이미지의 실행 버전은 프로필에서 확인하세요.

| 백엔드 | Python 3.14, Django 5.2.17 LTS, Django REST Framework 3.16.1 |
| 이미지 처리 | Pillow 12.3.0 |

기존 화면 구조를 유지하면서 로그인·프로필·목록·상세보기를 정리했고, 내보내기 대기 중
CPU 사용과 슬라이드쇼 이미지 로딩도 보완했습니다. 모든 의존성이 최신이거나 모든 보안
문제가 해소되었다는 의미는 아닙니다. 설치 환경에 맞는 접근 제어와 데이터 백업을 함께 유지하세요.

## SSO와 내부망 관리자 복구

로그인 창은 제공자별 아이콘을 사용하는 다크 카드로 표시한다. 활성 제공자만
노출하며 Authentik·Synology·Google·Microsoft·GitHub·범용 OIDC를 구분한다.
SSO와 비밀번호 로그인을 함께 허용하면 비밀번호 폼을 펼쳐 사용할 수 있고,
비밀번호 전용이면 바로 표시한다. SSO 전용 모드에는 비밀번호 입력 항목이 없다.
관리자 복구 화면은 같은 다크 스타일로 정리하며 모바일에서는 한 열로 표시한다.
아이콘과 스타일은 자체 서버에서 제공하고 기존 인증·내부망 제한은 변경하지 않는다.

내부 IP에서 SSO 로그인을 선택하면 인증을 시작하기 전에 제공자에 설정한 공개
HTTPS 주소로 이동한다. 인증과 로그인 완료는 공개 주소에서 처리하며 내부 IP로
돌아오지 않는다. IP와 도메인의 로그인 세션을 서로 복사하지 않는다. 이미 로그인한
주소에서 로그인 화면을 열면 홈으로 이동하며 관리자 복구 링크도 노출하지 않는다.
공개 프록시의 기존 HTTPS 강제 설정과 원래 Host 보존을 유지해야 한다.

초기값은 기존과 같이 비밀번호 로그인과 API 토큰 인증을 허용하고
활성 SSO 제공자는 없다. 업그레이드만으로 기존 계정·토큰이
차단되지 않는다. 슈퍼 관리자는 Django 관리자 화면에서 Authentik,
Synology SSO Server, Google, Microsoft, GitHub 또는 범용 OIDC 제공자를
복수로 등록할 수 있다. 표시된 제공자별 정확한 callback URL을 IdP에
등록하고, 공개 서비스 기준 URL과 명시한 HTTPS endpoint origin을 일치시켜야
한다. Microsoft는 `common`이 아닌 테넌트 UUID를 사용한다.

설정 화면은 제공자 종류에 필요한 입력란과 예시를 표시한다. Authentik은
Client ID·Client Secret·Discovery URL을 기본으로 입력하고 발급자와 서버 주소를
자동 확인한다. 표시 이름·순서·수동 발급자·별도 허용 주소는 접힌 고급 설정에 있다.
일반적인 자체 호스팅 IdP 접속에는 CIDR 입력이 필요 없다. 관리자 목록·설정의
**SSO 설정 가이드**에서 제공자별 등록 절차와 Discovery URL을 확인할 수 있다.
처음에는 비활성 상태로 저장해 고유 콜백 URI를 확정한 뒤 IdP에 등록한다.
가이드의 현재 접속 주소는 참고용이며, 실제 등록할 URI는 저장된 공개 서비스
HTTPS 주소를 기준으로 한다. 가이드는 설정을 자동 변경하지 않는다.

기존 사용자는 SSO 로그인만 하면 제공자가 검증한 이메일과 일치하는 계정 하나에
자동 연결된다. 비밀번호 일치나 사전 연결은 필요 없다. 미검증 이메일·동명이인·
중복 이메일·기존 제공자 연결 충돌은 자동 연결하지 않는다. 수동 연결·해제는
프로필 고급 항목에 남아 있으며 최근 재인증을 요구한다. Authentik의 HS256 전용
서명도 해당 Client Secret으로 검증하며 공개 키와 혼용하지 않는다.

신규 SSO 가입이 허용된 제공자에서는 인증 후 **Pinry 계정 만들기** 화면에서
아이디와 Pinry용 비밀번호·비밀번호 확인을 필수 입력한다. 이메일 앞부분을
아이디로 제안하지만 직접 수정할 수 있으며, 중복 아이디는 사용할 수 없다.
폼을 완료하기 전에는 계정이나 로그인 세션을 만들지 않는다. 가입 인증은
현재 브라우저에 한정해 10분간 유효하며 다른 탭에서 인증을 새로 시작했다면
이전 폼을 제출할 수 없다. 검증되지 않은 이메일은 자동 연결용으로 저장하지 않는다.

Pinry 비밀번호는 SSO 제공자에게 전송되지 않는다. 로컬 로그인이 꺼져 있어도
가입 시 비밀번호를 설정하지만 로그인에는 사용할 수 없다. 나중에 관리자가
로컬 로그인을 켜고 SSO를 끄면 가입 때 정한 아이디·비밀번호로 로그인할 수 있다.
기존 연결 계정은 가입 화면을 다시 거치지 않으며 비밀번호도 바뀌지 않는다.
기존 무작위 아이디 계정의 일괄 변경이나 별도 닉네임·공지 기능은 포함하지 않는다.

수동으로 연결하려면 **공개 주소에서 같은 Pinry 계정으로 로그인**한 후
프로필의 **고급: 수동 연결·연결 해제**를 펼친다. 현재 **Pinry 비밀번호**를
입력하고 **다시 인증**을 눌러 성공을 확인한 다음, 5분 안에 원하는 제공자의
**계정 연결**을 선택해 제공자에서 인증한다. Pinry와 제공자의 비밀번호를
같게 맞출 필요는 없다. 비밀번호 로그인이 꺼져 있으면 이미 연결된 SSO의
**다시 인증**을 사용한다. 계정 연결·재인증 POST는 다른 주소로 전달하지 않으며,
내부 주소에서 시작하면 공개 주소의 프로필에서 다시 진행하도록 안내한다.

재인증은 본인 확인이며 마지막 로그인 수단을 없앨 수 있는 허가는 아니다.
비밀번호 로그인이 꺼져 있고 다른 사용 가능한 SSO 연결도 없으면 **연결 해제**를
비활성화하고 사유를 표시한다. 재인증 만료와 마지막 로그인 수단 보호 오류는
서로 다른 안내로 표시한다.

비밀번호 로그인을 끄기 전에 현재 제공자의 슈퍼 관리자 SSO 로그인을
확인해야 한다. 별도의 최근 복구 로그인 확인은 강제하지 않는다. API 토큰
정책은 별도로 제어된다. 비활성화하면 기존 토큰을 삭제하지 않고
노출·발급·인증을 차단하며, 다시 허용하면 기존 자동화가 회복된다.

내부망 IP:포트로 직접 접속하면 **관리자 복구 로그인**을 사용할 수 있다.
활성 슈퍼 관리자 비밀번호, CSRF 검증, 반복 시도 제한, 15분 세션을 적용한다.
외부 프록시는 원래 Host와 전달 헤더를 보존해야 하며, 서비스 직접 포트를 인터넷에
포트 포워딩하지 않는다. 사설 IP 자체가 관리자 인증을 대신하지 않는다.
기존 전용 TLS 복구 포트도 유지한다. 자세한
설정·백업·셀 복구 절차는 [Synology 안내](deploy/synology/README_KO.md#sso와-복구-배포)를
따른다.

## 애니메이션 표시와 연속 감상

목록에서 두 프레임 이상인 GIF·WebP에만 `GIF ▶`·`WEBP ▶` 배지를 표시한다.
정적 GIF·WebP에는 배지를 표시하지 않으며, 썸네일은 기존대로 유지한다.
새 이미지는 등록할 때 판별 결과를 DB에 저장한다. 기존 이미지에는 nullable
`animation_status` 필드만 추가하며, 기동 시 전체 원본을 순회하지 않는다.
아직 판별하지 않은 기존 GIF·WebP는 해당 Pin을 처음 조회할 때 검사하므로
그 첫 조회에는 추가 파일 읽기가 발생할 수 있다. 이후에는 저장된 결과를 사용한다.
원본 파일·메타데이터·파일 수정 시각·썸네일은 이 판별 과정에서 변경하지 않는다.
읽을 수 없거나 손상된 원본은 배지를 생략하고 실패 결과도 저장해 반복 검사를
막는다. 파일을 외부에서 복구·교체한 경우 기존 판별 결과는 자동 갱신되지 않는다.

상세보기 상단의 이전·다음 버튼 또는 키보드 좌우 방향키로 현재 목록 순서대로
이동한다. 태그·사용자·보드 필터와 정렬을 유지하며, 필요한 경우 다음 페이지를
불러온다. `13 / 30+`처럼 뒤의 `+`는 아직 불러오지 않은 페이지가 있음을 뜻한다.
실제 끝에서는 순환하지 않고 다음 버튼을 비활성화한다.

빈 공간 클릭과 Esc 닫기, 닫은 뒤 기존 목록 위치는 유지한다.
모바일에서는 버튼을 사용하며 세로 스크롤·확대 제스처와 충돌할 수 있는
스와이프 이동은 추가하지 않는다. 고유 링크의 단독 Pin에는 이동 버튼이 없다.
이미지나 다음 페이지 로딩 실패는 상세창 안에서 안내한다.

이미지를 클릭하거나 하단 출처 왼쪽의 `원본 크기 (100%)`를 누르면 저장된
원본의 실제 크기로 확대하고 창 안에서 스크롤할 수 있다. 다시 누르면 화면에
맞춘다. `저장된 원본 열기`는 저장된 파일을 새 탭에서 열며, 외부 출처의
`원본 이미지` 링크와 구분된다. 선택한 보기 방식은 같은 브라우저·접속 주소에
저장되어 다른 Pin으로 이동하거나 상세보기를 다시 열고 새로고침해도 유지된다.
이미지가 바뀌면 스크롤 위치만 초기화한다. 저장소가 차단되면 현재 상세보기
안에서만 선택을 유지하며, 처음 사용하는 브라우저의 기본값은 화면 맞춤이다.

## 핀 목록 이미지 크기

정렬 도구 옆의 `이미지 크기`에서 `작게 · 보통 · 크게`를 선택한다.
데스크톱 카드 폭은 각각 160·240·320px이며, 보통은 기존 크기다.
화면 너비에 맞춰 열 수가 바뀌고 좁은 모바일 화면에서는 한 열로 표시한다.
작게 모드는 충분한 폭이 있는 모바일 화면에서 두 열을 사용할 수 있다.

선택은 같은 브라우저·접속 주소에서 기억한다. 목록·보드 안의 핀·검색 결과에
공통 적용되며 보드 목록 카드와 상세보기 원본 크기 설정은 변경하지 않는다.
크기를 바꿀 때 핀 목록을 초기화하지 않고 현재 선택과 정렬을 유지한 채
배치만 다시 계산한다. 브라우저 저장소가 차단되면 현재 목록에서만 유지한다.

## 브라우저 확장 프로그램

[SVRx Pinry Extension](https://github.com/sruinz/SVRx-Pinry-Extention)은
현재 페이지에서 여러 이미지를 선택하고, 공통 보드·태그·공개 범위를
지정해 한 번에 Pin으로 만드는 브라우저 확장 프로그램입니다.

서버 주소와 API 토큰은 확장 프로그램의 설정 화면에서 저장합니다.
[Chrome 웹 스토어](https://chromewebstore.google.com/detail/svrx-pinry/kgncmldoobdakadnojepmalpbmacoonh?authuser=0&hl=ko)와
[Microsoft Edge Add-ons](https://microsoftedge.microsoft.com/addons/detail/svrx-pinry/gmbgeiddpdblpjdbceoofclpeiikobjj)에서
설치하거나 GitHub에서 수동 설치할 수 있습니다. SVRx Pinry 확장은 Chrome·Edge를 공식
지원하고 Firefox는 공식 지원 대상이 아닙니다. 기존 Pinry용 Chrome·Firefox
레거시 확장은 단건 Pin 생성용입니다.

[확장 저장소](https://github.com/sruinz/SVRx-Pinry-Extention)의 소스로 수동
배포 후보를 만들려면 확장 저장소 루트에서 다음을 실행합니다.

```sh
bash scripts/package.sh
```

확장 ZIP은 서버 산출물과 같은 작업공간의 공통 `output/` 아래
`svrx-pinry-extension-<커밋 앞 12자리>/svrx-pinry-extension-0.1.0.zip`으로
생성됩니다.

## Synology Docker 이미지 만들기

현재 저장소는 완성된 Docker Hub 이미지를 전제로 하지 않습니다. 개발
PC에서 Synology용 산출물을 만든 뒤 NAS에 업로드해 이미지를 직접
빌드합니다.

저장소 루트에서 다음 명령을 실행합니다.

```sh
./scripts/create_synology_output.sh
```

기본 산출물은 저장소 루트 기준 `../output/`, 즉 저장소와 같은 작업공간의
공통 `output/` 폴더에 생성됩니다.

```text
<작업공간>/
├── <서버 저장소>/
└── output/
    ├── svrx-pinry-server-<서버 커밋 앞 12자리>/
    │   ├── svrx-pinry/
    │   ├── svrx-pinry-<서버 커밋 앞 12자리>.tar.gz
    │   ├── sw-transition/
    │   └── accept-tools/
    └── svrx-pinry-extension-<확장 커밋 앞 12자리>/
        └── svrx-pinry-extension-0.1.0.zip
```

생성된 압축 파일 또는 `svrx-pinry/` 폴더를 NAS에 업로드합니다. 이미지
빌드, Compose 실행 및 데이터 백업 방법은
[Synology 이미지 빌드 및 실행 안내](deploy/synology/README_KO.md)를
따르세요.

산출물에는 본 이미지 빌드·실행 파일, 기존 브라우저 캐시를
안전하게 전환하는 별도 `sw-transition/` context, 실제 NAS 복제본을
검증하는 선택 도구 `accept-tools/`가 들어갑니다. 데이터베이스,
업로드 이미지와 비밀키는 포함하지 않습니다.

기존 Pinry 또는 SVRx Pinry를 교체하며 같은 origin에 서비스 워커가
등록된 경우, NAS의 같은 작업 폴더에 main package와
`sw-transition/`을 **함께** 올립니다. `svrx-pinry-<커밋>.tar.gz`에는 main
package인 `svrx-pinry/`만 들어 있으므로, 압축 파일을 사용해도
`sw-transition/`은 디렉터리째 별도로 업로드해야 합니다. NAS에서 먼저
기존 main container를 중지해 2048 포트를 비운 뒤, Container Manager에서
`sw-transition/docker-compose.yml`을 사용하는 임시 project를 실행합니다.
이 project에는 데이터 마운트가 없으며 SSH 접속 없이 만들고 중지할 수
있습니다.

기존에 사용하던 모든 브라우저·확장 프로그램 클라이언트에서 전환 화면의
**전환 준비 완료**를 확인한 뒤 Container Manager에서 전환 project를
중지합니다. 그 다음 `svrx-pinry/`에서 본 이미지를 빌드하고 기존 Compose
project를 다시 실행합니다.
전체 명령과 이관 순서는
[Synology 이미지 빌드 및 실행 안내](deploy/synology/README_KO.md)를 따르세요.

## 최초 관리자 계정

신규 설치에서는 첫 번째로 성공한 웹 회원가입 계정이 자동으로 활성 상태의
Django 스태프 및 슈퍼유저가 됩니다. 설치한 서버를 운영할 사람이 다른
사용자보다 먼저 가입하세요.

기존 설치를 업그레이드할 때 활성 superuser가 이미 있으면 기존 권한을
변경하지 않습니다. 활성 superuser가 없으면 `(date_joined, id)` 순으로 가장
먼저 생성된 활성 계정 하나를 관리자 계정으로 한 번만 승격합니다. 활성
계정도 없다면 이후 첫 번째로 성공한 웹 회원가입 계정이 관리자 권한을
받습니다. 이 판정은 한 번만 완료되므로 관리자를 의도적으로 강등한 뒤에도
다른 계정이 자동으로 다시 승격되지는 않습니다.

현재 로그인한 활성 스태프 사용자는 자신의 프로필에 표시되는 **관리자
설정**을 통해 같은 서버의 `/admin/`으로 이동할 수 있습니다. 최초 관리자
지정 이후의 사용자 권한 변경은 이 Django 관리자 페이지에서 수행합니다.

## 관리자 태그 관리

관리자는 **관리자 설정 → Taggit → 태그**에서 태그를 검색하고 각 태그에
연결된 Pin 수를 확인할 수 있습니다. 개별 태그 화면에서는 이름을 변경하거나
태그를 삭제할 수 있습니다.

중복 태그를 합치려면 목록에서 두 개 이상의 태그를 선택한 뒤 **선택한 태그
병합**을 실행하고, 선택한 태그 중 유지할 대표 태그를 지정합니다. 모든 Pin
연결은 대표 태그로 이동하고 같은 Pin의 중복 연결은 하나로 정리되며, 나머지
태그는 삭제됩니다. 병합 작업은 태그 변경·삭제 권한이 모두 있는 관리자만
사용할 수 있으며 한 트랜잭션으로 처리됩니다. 대량 병합 전에는 데이터
폴더를 백업하세요.

## 복수 태그 검색

검색 화면에서 태그를 하나 이상 선택할 수 있습니다. 여러 태그를
선택하면 선택한 태그를 **모두** 포함한 Pin만 표시합니다. 예를 들어
`여행`과 `야경`을 같이 선택하면 두 태그가 모두 연결된 Pin이
결과에 나옵니다.

기존의 단일 태그 링크와 `/pins/tags/<태그>` 주소는 그대로
작동합니다. API 클라이언트는 같은 `tags__name` 쿼리 파라미터를
반복해 같은 AND 검색을 사용할 수 있습니다.

```text
/api/v2/pins/?tags__name=여행&tags__name=야경
```

## Pin의 보드 포함 상태

Pin의 보드 추가 화면은 현재 로그인한 사용자가 소유한 보드를
기준으로 포함 상태를 표시합니다. 다른 사용자가 등록한 Pin을 내
보드에 넣은 경우에도 **이미 포함됨**으로 표시되며 다시 선택할 수
없습니다.

보드 소속 정보는 상세 보기의 보드 추가 화면에서만 조회합니다.
다른 사용자의 보드 정보나 메인 Pin 카드에는 소속 보드를
노출하지 않습니다. 포함 상태를 불러오지 못하면 중복 여부를 확인할
수 없으므로 추가 버튼을 비활성화합니다.

## Pin·보드 원본 내보내기

로그인한 사용자는 자신이 소유한 보드 또는 선택한 Pin에서 **미리보기 →
내보내기**를 실행하고, 이후 **내 메뉴 → 내보내기**에서 진행 상태와 완료
파일을 확인할 수 있습니다. 브라우저를 닫아도 작업은 계속됩니다. 컨테이너가
정상 중지된 뒤 다시 시작되면 최근 확정된 스냅숏과 시도 지점에서 안전하게
재개하며, 만들던 부분 ZIP을 다운로드 대상으로 공개하지 않습니다.

내보내기를 확정하면 그 시점의 대상 Pin 목록을 고정하므로 이후 보드에 새로
추가한 Pin은 진행 중인 ZIP에 포함되지 않습니다. 대상 Pin의 설명·태그와 원본
파일은 백그라운드 작업자가 안전한 스냅숏을 만들 때 확정됩니다. 이미 복제한
항목은 원본 Pin이 삭제되어도 스냅숏 시점의 내용으로 계속 처리합니다. 스냅숏
전이나 생성 중에 본인 Pin의 원본이 사라지거나 바뀌어 일관성을 보장할 수
없으면 부분 결과를 내놓지 않고 해당 작업을 실패로 표시합니다.

완료 ZIP은 완료 시각부터 **최대 24시간** 다운로드할 수 있습니다. 24시간은
내보내기를 실행하는 주기나 일일 횟수 제한이 아니므로 진행 중인 작업이
없으면 새 내보내기를 시작할 수 있습니다. 새 내보내기가 성공하면 이전 성공
ZIP을 즉시 교체하여 더는 다운로드할 수 없고, 새 작업이 실패하면 이전 성공
ZIP은 원래 만료 시각까지 유지됩니다. 만료된 ZIP과 오래된 작업 파일은
작업자가 보관 정책에 따라 정리합니다.

ZIP에는 Pin마다 원본 이미지와 XMP 사이드카가 한 쌍씩 들어가고 Pin
메타데이터는 `manifest.json`에도 기록됩니다. 원본 이미지 바이트와 이미지에
이미 들어 있던 EXIF·IPTC·XMP는 변경하지 않습니다. Pin 등록일
(`Pin.published`)·설명·태그는 XMP와 매니페스트에 보존하며, ZIP 이미지와 XMP
엔트리의 수정 시각도 ZIP 형식이 표현할 수 있는 범위에서 Pin 등록일을
사용합니다. 정확한 UTC 등록일은 XMP와 `manifest.json`의 값입니다.

ZIP의 `originals/`는 UUID별 하위 폴더가 없는 단일 폴더입니다. 가능한 경우
원본 파일명을 유지하고, 운영체제에서 사용할 수 없는 문자는 안전하게
정규화합니다. 대소문자를 구분하지 않았을 때 같은 파일명이 겹치면 확장자
앞에 `__<짧은 식별자>`를 붙여 덮어쓰기를 막습니다. 같은 원본 이미지를
공유하는 Pin도 각각 이미지·XMP 한 쌍을 가지며, 파일과 Pin의 정확한 연결은
`manifest.json`을 기준으로 확인합니다.

스냅숏과 최종 게시 직전 권한 검사에서 삭제되었거나 비공개로 바뀐 타인의
Pin은 안전하게 제외됩니다. 반면 본인 Pin의 원본이 사라졌거나 바뀌어 안전한
스냅숏을 만들 수 없으면 부분 ZIP을 제공하지 않고 작업 전체를 실패로
표시합니다. 계정마다 한 번에 하나의 작업을 요청할 수 있고, 서버는 ZIP 생성
작업을 하나씩 순서대로 처리합니다. 화면의 **작업자 대기 중**은 작업자가
시작하는 중이거나 앞선 작업의 완료를 기다리는 상태이지 서비스 장애를 뜻하지
않습니다. 저장소 오류·용량 부족·만료가 표시되면 안내된 재시도 가능 여부를
확인하고 DSM **Container Manager → 컨테이너 → svrx-pinry → 로그**에서 오류
코드를 확인하세요.

내보내기에는 예상 ZIP 크기 외에 스냅숏과 안전한 파일 게시를 위한 여유
공간이 필요합니다. `/data/exports`와 그 아래의 `.staging`, `ready`를 수동으로
삭제하거나 소유자·권한을 바꾸지 마세요. 데이터 폴더를 백업할 때는 이 경로도
운영 데이터로 함께 취급합니다. 반대로 배포용 Synology 산출물과 Docker build
context에는 데이터베이스, 업로드 미디어, export ZIP, 사용자 계정, 비밀키가
포함되지 않습니다.

## 기존 Pinry 데이터 자동 마이그레이션

Synology 산출물의 Compose 파일은 컨테이너를 시작할 때 기존 데이터를
자동으로 판별합니다. 빈 데이터 폴더를 사용하는 신규 설치나 이미 현재
형식으로 전환된 SVRx Pinry는 마이그레이션을 건너뛰고 정상 서비스를
시작합니다. 기존 Pinry 데이터나 갱신이 필요한 SVRx Pinry 데이터가 있으면
별도의 SSH 명령 없이 다음 작업을 자동으로 수행합니다.
미디어와 무관하다고 명시적으로 검증된 DB schema 갱신은 전체 이미지를
다시 검사하지 않고 표준 Django migration으로 빠르게 적용합니다.
현재 빠른 경로의 정확한 허용 목록은
`django_images.0007_startup_validation_state`,
`users.0002_admin_bootstrap`, `exports.0001_initial`,
`exports.0002_exporttarget_identity_snapshot`입니다. 이 목록 밖의 알 수
없거나 미디어 관련 변경은 기존 안전 절차를 유지합니다.

1. 기존 SQLite 데이터베이스의 온라인 스냅샷과 무결성 검사를 수행합니다.
2. 기존 미디어를 UUID·원본 파일명 기반의 현재 저장 구조로 옮깁니다.
3. 확정된 배치 단위로 진행 상태를 기록해 정상 재시작 시 이어서 처리합니다.
4. 최종 검증이 끝나면 기존 파일을 `data/legacy-backup/<실행 ID>/`에
   보존하고 SVRx Pinry 서비스를 시작합니다.

마이그레이션 전에는 기존 컨테이너를 중지하고 데이터 폴더 전체를 별도
위치에 백업해야 합니다. 기존 데이터 경로를 계속 마운트하거나 그 **내용
전체**를 새 `data` 폴더로 복사할 수 있으며, `data/data`처럼 한 단계 더
중첩되지 않도록 주의합니다. 제공된 Compose 파일의 자동 마이그레이션
`command` 항목은 제거하지 않습니다.

작업 중에는 같은 접속 주소에 한국어 진행 화면이 표시되고 일반 API와
미디어 요청은 안전하게 차단됩니다. 브라우저를 닫아도 작업은 계속되므로
컨테이너·프로젝트를 강제 종료하거나 데이터 폴더를 수정하지 마세요. 정상
중지 후 다시 시작하면 마지막 확정 배치부터 재개합니다. 완료되면 별도
조작 없이 일반 서비스로 전환됩니다.

SA6400 검증 환경에서는 이미지 레코드 346개와 참조 미디어 파일 1,384개의
이관이 2분 이내에 완료되었습니다. 실제 소요 시간은 NAS 성능, 저장 장치와
이미지 크기에 따라 달라질 수 있습니다.

진행 상태는 `/migration/` 또는 `/migration-status.json`에서 확인할 수
있습니다. 오류는 **재시도 가능**, **사용자 조치 필요**, **치명적**으로
구분되며, 데이터가 불완전한 상태로 서비스를 시작하지 않고 원본과 백업을
보존합니다. 화면의 오류 코드와 DSM Container Manager 로그를 함께
확인하세요.

자세한 데이터 경로 준비, 서비스 워커 전환, 상태 경로, 백업 구조와 롤백
절차는 [Synology 이미지 빌드 및 실행 안내](deploy/synology/README_KO.md)에
정리되어 있습니다.

## 실행 버전 확인

산출물의 `BUILD_INFO`, Docker 이미지 레이블과 실행 중인 서버는 같은 Git
커밋을 표시합니다. 로그인 후 **내 메뉴 → 프로필 → 빌드 정보**에서 짧은
커밋 값을 확인하거나 다음 API를 사용할 수 있습니다.

```sh
curl -s http://NAS주소:2048/api/v2/version/
```

같은 `latest` 태그로 이미지를 다시 빌드했다면 Compose에서 컨테이너를
강제로 다시 생성해야 새 이미지가 실행됩니다.

```sh
docker compose up -d --force-recreate
```

## 데이터 보존

기본 Compose 설정은 `/volume1/docker/svrx-pinry/data`를 영구 데이터
경로로 사용합니다. 이 폴더에는 데이터베이스, 업로드 이미지와 서버 설정이
저장됩니다. 컨테이너나 이미지를 교체하기 전에 해당 폴더를 백업하고 직접
삭제하지 마세요.

## 기동 복구 패치 이력

`fix/startup-recovery-patch`는 운영 기준 `64388c7`에서 분리한 긴급 패치다.
당시에는 현대화 작업선과 별도로 배포했으며 Python·Django·Vue 버전과 DB 스키마,
기존 데이터 경로와 Synology 빌드 방식을 변경하지 않았다. 현재 메인 통합에는 이 패치의 후속 변경도 포함한다.

- 기동 작업자의 완료 보고 뒤 종료 유예를 1초에서 15초로 늘려 짧은 대기로
  정상 종료를 오류로 판정하는 경우를 줄인다. 완료·종료 증거 검증은 유지한다.
- 안전하게 복구 가능한 기동 실패에 `서버 재시동` 버튼을 제공한다.
  NAS나 Docker를 재부팅하는 버튼이 아니라 Pinry 기동 절차를 다시 시도한다.
- 정상 서비스의 `/migration/`, `/migration/index.html` 요청은 Nginx에서
  바로 메인 페이지로 보낸다. 정상·기동 진행 상태에서는 재시도를 허용하지 않는다.
- 재시도는 서버 전체 30초 간격·시작 관리자 실행당 최대 3회이며,
  오류 종류·잠금·자식 종료·요청 출처·일회성 자격을 확인한다.

버튼은 모든 오류를 강제로 해제하지 않는다. 설정·데이터 검증 실패와
안전 상태를 확인할 수 없는 오류에는 관리자 확인이 필요하다.
이미 구 버전으로 오류 화면에 멈춘 컨테이너에는 새 이미지를 적용해야 한다.
자세한 빌드·적용 절차는 [Synology 안내](deploy/synology/README_KO.md)를 따른다.
